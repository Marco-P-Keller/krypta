## Run-Reihenfolge & Begründung

Die Reihenfolge ist nach **„Konsequenz bei Bug" + „Reasoning-Tiefe"** gestaffelt — schwierigste & folgenschwerste Bereiche zuerst, während Kontext maximal frisch ist.

| Run | Bereich | Warum diese Position | Geschätzter Umfang |
|-----|---------|----------------------|-------------------|
| **0** | **Setup** (dieser Run) | Branch, Scope, Plan, Audit-Trail-Sichtung | ✓ done |
| **1** | **Kryptographie** | Höchste Konsequenz bei Bug, schwerstes Reasoning. Frischer Kontext nutzen. | ~6–8h |
| **2** | **Protokoll** | Hat viel State + Vorgeschichte (`_seq`/`_psid`). Baut auf Run 1 auf. | ~6–8h |
| **3** | **State & Concurrency** | Klassische Bug-Brutstätte. Race-Conditions brauchen tiefe Code-Reads. | ~6h |
| **4** | **Storage & Key Management** | iOS-spezifisch + crash-safety. Kann teilweise auf Run 3 aufbauen. | ~5h |
| **5** | **Netzwerk** | Überschaubarer als die obigen, defense-in-depth | ~3–4h |
| **6** | **Client / Business Logic** | Wenig Krypto, mehr UX-Sec. Lockout, Workflow, Memory. | ~4h |
| **7** | **Cross-Cutting Integration** | Konsistenzprüfung über alle Bereiche, Multi-Komponenten-Angriffe, Final-Report | ~3–5h |

## Pro-Run Workflow (verbindlich)

```
PHASE A — Analyse
  1. Relevanten Code in Kontext laden (Files, Funktionen, Imports)
  2. Komponentenkarte zeichnen (was ruft was, welcher State)
  3. Threat-Modeling: pro Komponente "was würde Angreifer X tun?"
  4. Findings-Tabelle: ID, Severity, Datei:Zeile, Angriffs-Szenario, Root Cause

PHASE B — Pro Finding
  1. PoC-Test schreiben unter test/audit/2026-05-area<N>/
     → Test demonstriert den Angriff, ist anfangs ROT
  2. Fix-Patch implementieren (unstaged)
  3. PoC-Test wird GRÜN
  4. Alle bestehenden Tests bleiben GRÜN: `flutter test`
  5. Static Analysis sauber: `flutter analyze lib/`

PHASE C — Adversarial Review
  1. `cd /c/dev/kryptarich && codex review --uncommitted`
     (Codex sieht den vollen unstaged Diff inkl. Test + Fix)
  2. Codex-Findings einlesen, in den Bericht übernehmen
  3. Echte Probleme: zurück zu Phase B
  4. False Positives: dokumentieren mit Begründung
  5. Wiederholen bis Codex 2 RUNDEN HINTEREINANDER 0 Critical/High meldet

PHASE D — Daniel-Review & Commit
  1. Bericht-Entwurf zeigen: docs/audit/2026-05-area<N>-<name>.md
  2. Daniel reviewt unstaged diff via `git diff`
  3. Daniels schriftliches OK → Commit
     Message: "audit(2026-05): area<N> <name> — <X>C/<Y>H fixes (codex-approved)"
  4. Bericht finalisieren mit Final State pro Finding
```

---

## Codex-Aufruf — Konkret

**Standard-Befehl (nach Phase B):**

```bash
cd /c/dev/kryptarich
codex review --uncommitted
```

`codex review --uncommitted` akzeptiert keinen Custom-Prompt. Falls wir adversariale Hinweise mitgeben wollen (z.B. „Fokus auf Race Conditions"), nutzen wir alternativ:

```bash
cd /c/dev/kryptarich
git diff > /tmp/audit-diff.patch
codex exec --skip-git-repo-check "Du bist adversarial Security-Reviewer für ein E2E-Messaging-System. \
Hier ist ein Diff aus einem aktiven Audit (Bereich: <NAME>). \
Versuche aktiv jeden Fix zu brechen. Suche: \
  - Race Conditions \
  - Replay/Rollback-Bypässe \
  - State-Inkonsistenzen \
  - Edge Cases bei Crash-Recovery \
  - Cross-Component-Angriffe \
Pro Finding: Severity, Angriffsszenario, betroffene Zeilen. \
Diff folgt:" < /tmp/audit-diff.patch
```

Der zweite Weg ist explizit adversarial. Default für jede Runde: zuerst `codex review --uncommitted` (sein Standard-Mode), bei Bedarf zweiter Pass mit dem adversarialen Prompt.

## Tracking pro Bereich

Pro Run wird im Bericht (`docs/audit/2026-05-area<N>-*.md`) eine Findings-Tabelle geführt:

| ID | Severity | Datei:Zeile | Angriff | PoC-Test | Codex-Runden | Status |
|----|----------|-------------|---------|----------|--------------|--------|
| A1 | High | foo.dart:123 | Replay via X | test/audit/.../a1_test.dart | 2 | APPROVED |

Nicht-akzeptierte Codex-Findings werden mit Begründung als „dismissed" geführt.

## Was passiert bei Blockern

- **Codex findet etwas, das ich nicht selber lösen kann:** Eskalation an Daniel mit klarer Beschreibung. Kein Hack-Workaround.
- **Bestehender Test bricht durch Fix:** Erst Root-Cause, dann ggf. Test anpassen WENN Test fehlerhaft war, sonst Fix überdenken.
- **Findings-Tiefe sprengt Run-Scope:** Run abschließen für gefundene Items, neuen Bereich-Run für Tiefenuntersuchung anhängen.
