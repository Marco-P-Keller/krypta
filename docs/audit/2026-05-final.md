## 1. Executive Summary (honest, not optimistic)

Seven audit runs through Krypta's cryptography, protocol, state, storage, network, and client layers turned up **two classes of issue that mattered most:**

1. **Architecture-level cryptographic gaps** that were already known design choices but had never been hardened to defense-in-depth (signing-key TOFU pin, AAD binding for at-rest and password-protected payloads).
2. **Bugs that would silently break production functionality**, found in places that were not exercised by existing tests:
   - Firestore rules missing for `deliveryTokens` and `keyCommitments` (sealed sender + transparency entirely denied)
   - Firestore writes missing the `updatedAt` field that rules required (registerPublicKey, publishPreKeyBundle, registerFcmToken all denied)
   - Catastrophic data-loss path in `pruneOrphanChatFiles` — a single transient `chats.enc` decrypt failure on boot would have wiped every ratchet session

The crypto primitives themselves are still solid; failures were in **wiring, enforcement, and back-end-rules-vs-code coupling**.

**One fundamental residual:** the H1-Crypto fix closes every TOFU-bypass once a chain is bootstrapped, but the *first-contact* signing-key pin is itself unverifiable without XEdDSA (which `cryptography` package does not provide). Documented in §6 of `2026-05-area1-cryptography.md`. Recommended follow-up: extend Safety Number to bind the signing key (smaller scope than implementing XEdDSA).

## 4. Cross-cutting consistency

I checked that the per-area fixes do not contradict each other or open new attack paths via composition.

| Concern | Status |
|---------|--------|
| H1-Crypto pin storage + H1-Storage trustworthy-flag — does the pin get pruned? | No: `pruneOrphanChatFiles` only touches `msg_*` / `ratchet_*`, not `kt_pin_*`. `clearLog(userId)` and `clearAll()` already remove pins (Run 1 fix). ✅ |
| H2-Crypto AAD on encrypted storage + H1-Storage data-loss guard — does the auto-migrate fire when chats list is empty-but-untrustworthy? | The auto-migrate fires per slot on read; it never depends on `_chats`. Untrustworthy chats does not prevent migration. ✅ |
| H1-Proto + H1-State per-chat ratchet mutex — does the mutex deadlock under nested send-from-receive? | No nested send-from-receive paths exist (control messages are sent under their own mutex acquire, not from inside a decrypt). ✅ |
| H4-Crypto `pwd-v1\|sender\|recipient\|messageId` AAD — both sides know all three? | Sender uses `userId!` (self) + `chat.recipientId` + `messageId`; receiver uses `msg.senderId` + `msg.recipientId` + `msg.id`. All three fields are stable cross-device. ✅ |
| H1+H2-Network rules + H2-Crypto v3 password format on encrypted message | Rules allow `pw is bool` on outer message; v3 password blob lives in inner encrypted payload. No interaction. ✅ |
| H1-Network deliveryTokens rule + H4-Crypto AAD — does the rule allow tokens needed for routing? | Yes: read by anyone authenticated, write only by owner. ✅ |

No cross-component regressions found.

## 7. How close to "audit-ready"?

**Same answer as 26.04., updated:**

On the code side, with this audit's fixes, Krypta is **measurably stronger than at 26.04.** — two HIGH bugs that silently broke production functionality (Firestore rules + missing updatedAt) are gone, the data-loss path on transient decrypt failure is closed, and the cryptographic envelope (per-chat ratchet mutex, signing-key TOFU pin, AAD binding everywhere) is more robust against composition attacks.

On the process side, the same gaps still exist:
- Threat model not consolidated into a single versioned doc.
- No formal protocol description for the Krypta-specific additions (`_seq`, `_psid`, sealed sender v3, identity-bound delivery tokens, control-message HMAC binding, KeyCommitment v2 with TOFU pin, password v3 with cross-device AAD).
- No symbolic verification of protocol composition.
- No hardware-attested device integrity on Android.
- **No independent professional pentest on a released build.**

**My honest recommendation (unchanged from 26.04.):** do not ship to production yet. The code is in a strong state for Daniel to commit & push, run a manual read-through, then engage either a human cryptography review or a boutique mobile security firm before a public release. Audit-readiness *work* is at maybe **88%** (up from 80%); audit-readiness *signal* (independent human review) is still 0%.
