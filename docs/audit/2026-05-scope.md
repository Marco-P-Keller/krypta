## 3. Out-of-Scope (explizit, nicht als Findings melden)

- **Group Messaging / Sender Keys** — nicht erwünscht
- **Multi-Device Support** — nicht erwünscht
- **Encrypted Backups** — nicht erwünscht

Begründung: Bewusst aus dem Threat-Model entfernt (siehe `out_of_scope` in User-Memory). Diese Features würden Identity-Keys verteilen, langlebige exfiltrierbare Datenkopien erzeugen oder Sender-Keys + Member-Management verlangen — alles gegen den Single-Device / Ephemeral / Zero-Backup-Ansatz.

Außerdem out-of-scope für AI-Audit (in §7 dokumentieren, nicht „beheben"):
- Real-Hardware-Timing-Side-Channels (Argon2, HMAC, AEAD)
- Formale Protokoll-Verifikation (ProVerif, Tamarin)
- iOS/Android OS-Bugs (Keystore, Secure Enclave)
- Black-Box-Pentest auf realer Hardware

## 4. Threat Model (kompakt)

**Schutzziel:** Vertraulichkeit + Integrität + Forward Secrecy + Post-Compromise Recovery für 1:1-Messaging zwischen zwei iOS/Android-Devices.

**Angreifer-Kategorien (in absteigender Priorität):**

1. **Server / Backend kompromittiert (Firestore/FCM/Cloud Functions).** Sieht alle Metadaten, kann Nachrichten umleiten, beliebige Inhalte einschleusen. Darf NICHT Klartext lesen oder Identitäten verifizieren können.
2. **Netzwerk-Angreifer mit gültigem CA-Zertifikat.** Aktives MITM. Pinning muss greifen.
3. **Physischer Zugriff auf gesperrtes Gerät.** Rateversuche, Cold-Boot, Disk-Forensik. Vault-Lockout + Emergency-Wipe + at-rest-Verschlüsselung müssen halten.
4. **Malware auf entsperrtem Gerät.** Frida, Debugger, Repacking. Device-Integrity-Policy + periodische Checks müssen entdecken.
5. **Kompromittierte Peer-Identität (gestohlene Session).** Forward Secrecy + Anti-Rollback müssen Schaden zeitlich begrenzen.
6. **Unzuverlässige Peers (Junk-Payloads, Integer-Abuse, malformed Frames).** Eingangsvalidierung muss Crash + State-Korruption verhindern.

**Was NICHT geschützt werden muss:**
- Schutz vor dem Geräteeigentümer selbst (kein DRM-Modell)
- Schutz vor staatlichen Akteuren mit Kernel-Zugriff
- Schutz vor Hardware-Angriffen auf Secure Enclave / Strongbox

## 6. Stop-Kriterium pro Audit-Bereich

Ein Bereich gilt als „closed", wenn ALLE folgenden Bedingungen erfüllt sind:

1. **Codex zwei aufeinanderfolgende Runden** (`codex review --uncommitted` mit explizitem „break this"-Prompt) ohne neue Critical/High-Findings.
2. **Jedes Critical/High-Finding** hat einen **PoC-Test** im Repo, der den Angriff demonstriert (rot vor Fix, grün nach Fix).
3. **Alle bestehenden Tests** (Stand Branch-Start: 342, ggf. inzwischen mehr) bleiben grün.
4. **`flutter analyze lib/`** sauber.
5. **Daniel gibt schriftlich OK** (in dieser Session) pro Fix-Set, dann erst Commit.

Findings, die nach §3 explizit out-of-scope sind, werden im Bericht als „dismissed (out-of-scope per Threat Model)" geführt, nicht als Risiko.

## 7. Reporting

Pro Audit-Bereich entsteht ein Report unter:
`docs/audit/2026-05-area<N>-<area-name>.md`

Final-Report nach Run 7:
`docs/audit/2026-05-final.md`

Format pro Finding:
- ID, Severity (Critical/High/Medium/Low)
- Angriffsszenario (konkret, nicht generisch)
- Root Cause mit Datei + Funktion + Zeilennummer
- PoC-Test (Datei + Funktionsname)
- Fix als Diff-Beschreibung + tatsächlicher Patch
- Codex-Review-Loop (Round-by-Round, was Codex sagte, wie behoben)
- Final State (APPROVED nach N Runden)

## 8. Commit-Disziplin

- **Audit-Branch:** `audit/2026-05`. Alle Arbeit hier.
- **Keine Commits** ohne (a) Codex-Approval pro Bereich UND (b) Daniels schriftliches OK in dieser Session.
- Wenn ein Bereich abgeschlossen ist: **ein** Commit pro Bereich, mit Message-Format:
  `audit(2026-05): area<N> <name> — <X> critical, <Y> high fixes (codex-approved)`
- Patches dazwischen bleiben unstaged. Daniel sieht Diff via `git diff` bevor er OK gibt.

## 9. Verbindliches Workflow-Schema

```
Pro Bereich:
  1. Tiefe statische Analyse + Threat-Modeling der Komponente
  2. Findings-Liste mit Severity
  3. Pro Finding:
     a) PoC-Test schreiben (rot)
     b) Fix-Patch (unstaged)
     c) PoC-Test grün, alle anderen Tests grün, analyzer sauber
  4. `codex review --uncommitted` (Codex bekommt den vollen Diff)
  5. Codex-Findings einarbeiten → zurück zu 3
  6. Wiederholen bis Codex 2 Runden hintereinander 0 Critical/High meldet
  7. Daniel-Review → OK → Commit für diesen Bereich
  8. Bereich-Report finalisieren in docs/audit/2026-05-area<N>-*.md
```
